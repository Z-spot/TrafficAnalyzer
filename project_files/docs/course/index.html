Each frame needs a time, from the file

Speed comes from time, so every frame needs a correct time stamp. The program reads the times that the camera wrote into the file, and does not assume a fixed rate.

CODE 

gaps = np.diff(pts)
if gaps.min() <= 0 or gaps.max() > 1.5 * np.median(gaps):
    raise ValueError(f"unexpected frame gaps in ticks: ...")
return (pts - pts[0]) * num / den
PLAIN ENGLISH

Measure the gap between every pair of neighbouring frames.

If any gap is zero or negative, or far longer than normal, a frame has gone missing or been repeated.

In that case, stop with an error rather than hand back wrong times.

Otherwise, count from the first frame and convert the ticks into seconds.

💡
Why not just use 30 frames per second?

Frames are not spaced evenly. Gaps vary by about 5 percent, and an assumed rate drifts away from the real clock with no warning.

Reading frames in order

The program reads the video one frame at a time, from the start. It skips ahead by reading past frames without turning them into pictures, because that is faster.

CODE 

for idx in range(start_frame, end_frame):
    ok, frame = cap.read()
    if not ok:
        return
    yield idx, frame
PLAIN ENGLISH

For each frame number in the range we want.

Ask the video reader for the next picture. It also says whether the read worked.

If the read failed, the video has run out, so stop cleanly.

Otherwise, hand back the frame number and the picture, one at a time, so memory stays small.

02

The spotter

How a trained model finds a car in one picture, and how sure it is about what it found.

A model that has already seen many streets

The spotter is a neural network called YOLO. Someone else trained it on a large photo collection, so we do not train anything ourselves.

The trained numbers are stored in a file called the weights file, here yolo26m.pt. The collection it learned from is called COCO.

🚗
car (class 2)

Most of the traffic at this junction

🛵
motorcycle (class 3)

Small and often missed, a known weak spot

🚌
bus (class 5)

Large, so usually easy to see

🚚
truck (class 7)

Large, sometimes confused with a bus

Every detection has three parts

For each car it finds, the spotter returns a box around it, a class, and a confidence score.

1
The box

Four numbers: the left, top, right and bottom edges, in pixels.

2
The class

Car, bus, truck or motorcycle, as a number from the model's list.

3
The confidence

How sure the model is, from 0 to 1.

🔎
Why keep the unsure ones?

The pipeline keeps detections down to a confidence of 0.10, on purpose. The tracker uses those weaker boxes to keep a car going between frames, so throwing them away early would cut cars short.

The code that asks the model

One call to the model handles a whole frame. Every setting it uses comes from config/pipeline.yaml, not from the code.

CODE 

res = self.model.predict(
    frame, imgsz=self.cfg["imgsz"], conf=self.cfg["conf"], iou=self.cfg["iou"],
    classes=self.cfg["vehicle_classes"], device=self.cfg["device"], verbose=False,
)[0]
PLAIN ENGLISH

Give the model one picture and ask it to look for objects in it.

Shrink the picture to the size set in the config, then discard anything below the confidence floor.

Only look for the vehicle classes listed in the config, and run on the Mac's graphics chip.

Take the result for this one picture, which is the first item in the list.

💡
Bigger is slower, but sees more

imgsz sets the size the model looks at, 1280 pixels on the long side here. The camera frame is 3840 pixels wide, so the picture is shrunk to a third. Small, far-away cars lose detail in that shrink.

What the spotter sees, and what it misses

The spotter is good at some cars and weak at others. Knowing which is which tells you where the rest of the pipeline has to help.

✅

Near cars

Large and clear, so the confidence is high and the box is steady.

🔭

Far cars

Small and faint. The spotter sees them, but only just, with low confidence.

🙈

Hidden cars

A car behind a bus has no picture to find, so nothing is detected for a while.

🛵

Motorcycles

Small and thin, so the spotter misses many of them. This is a known issue, and it is deferred.

03

Name badges

How the tracker gives one car the same ID in every frame, and what makes it lose that ID.

The spotter forgets everything

The spotter looks at each picture alone. It has no idea that the car in frame 300 is the same car as in frame 301.

The tracker adds that memory. It gives every car a track ID, which we can think of as a name badge.

🏷
How the tracker decides it is the same car

It predicts where each car should be in the next frame, using its recent motion. Then it matches each new box to the nearest prediction that makes sense.

The code that hands out badges

Every frame goes to the tracker, one at a time, in order. The tracker returns the same boxes, now with an ID attached.

CODE 

det = tracker.update_with_detections(det)
det = det[det.tracker_id != -1]
if len(det) == 0:
    continue
PLAIN ENGLISH

Give the tracker this frame's boxes. It returns them with badges where it has matched them.

Keep only the boxes that now have a badge. The rest are not confirmed yet.

If nothing is left, there is nothing to record for this frame.

Move on to the next frame.

⚠️
Empty frames still matter

When a frame has no cars at all, the code still sends the tracker an empty set of boxes. The tracker counts frames to decide when a badge has expired, so skipping a frame would make it wrong.

The three settings that decide a badge's life

Three numbers in config/pipeline.yaml control when a badge is handed out and when it is taken back.

track_activation_threshold: 0.25 A new car needs a score of 0.25 plus 0.1, which is 0.35, before it gets a badge. Weak boxes can still keep an existing car going.
lost_track_buffer: 30 A car that disappears keeps its badge for 30 frames, about one second. After that the badge is retired.
minimum_matching_threshold: 0.8 How well a new box has to line up with a prediction before the tracker accepts it as the same car.

04

The film editor

Raw tracks are messy. The editor throws away parked cars, joins broken pieces and steadies the boxes.

Keep only the cars on the road

The tracker follows everything, including parked cars. The road test decides which tracks to keep, using the bottom centre of each box, the point where a car meets the ground.

CODE 

on_road = points_inside(traj[["anchor_x", "anchor_y"]].to_numpy(), polygons)
fraction = pd.Series(on_road, index=traj.index).groupby(traj.track_id).mean()
keep = fraction[fraction >= min_fraction].index
PLAIN ENGLISH

For every box, mark True if its bottom centre is inside the road outline, otherwise False.

For each track, average those True and False marks. That gives the share of its frames spent on the road.

Keep the tracks where that share is at least the minimum, which is 0.5 in the config.

💡
Why judge the whole track?

A car on the kerb edge would flicker in and out of the outline frame by frame. Judging each track as a whole keeps one continuous track for that car.

Six cuts, in order

After the road test, the editor makes six passes over each track. Each one fixes a different problem.

1
Vote on the class

A track is sometimes called a car and sometimes a truck. The class with the most total confidence wins, for the whole track.

2
Stitch broken tracks

Join a track's end to another track's start, if they are very likely the same car.

3
Vote on the class again

Joined tracks can disagree, so the vote is run once more.

4
Fill short holes

Where a car was missed for a few frames, draw its box in between, on a straight line.

5
Drop fragments

Tracks shorter than 15 frames, about half a second, are too short to be a real car.

6
Steady the boxes

Average each box over neighbouring frames, so it glides rather than jitters.

Joining a broken track

When a car's badge is lost and then handed out again, the editor checks whether the two pieces fit. It predicts where the first piece should be when the second begins, and then measures how far off it is.

CODE 

err = (err_fwd + err_bwd) / 2
if err <= cfg["stitch_base_tol_px"] + cfg["stitch_tol_per_frame_px"] * gap:
PLAIN ENGLISH

Average the two prediction errors, one from each direction in time.

The longer the gap, the more the car could have moved, so the allowed error grows with the gap.

Only join if the error is inside that allowance.

🚙

Same class

A car is never joined to a bus.

📏

Close enough

The predicted position must match, within a tolerance of 60 pixels plus 3 per missing frame.

⚖️

No close rival

If two candidates are about equally good, the editor joins neither.

⚠️
Why the rival check matters

Cars stopped in a queue look almost identical and sit close together. Joining the wrong pair would swap two cars, so the editor refuses to guess.

Steadying the boxes

Detected boxes wobble by a few pixels from frame to frame. The editor takes a rolling average over neighbouring frames, so the box moves smoothly.

CODE 

cx, cy = roll(cx, box_window), roll(cy, box_window)
w, h = roll(w, size_window), roll(h, size_window)
PLAIN ENGLISH

Average the centre of each box over about 7 frames, centred on the frame being fixed.

Average the width and height over a longer window, about 15 frames, so the size settles more slowly.

05

The saved game

Why the slow step is saved, what each output file holds, and what is still open.

Save the slow part

Detection is the slow step. On the 30-second test run it takes about 0.13 seconds per frame, so the full 21-minute video would take about 84 minutes.

The program keeps those detections in a cache. Every later stage reads that copy, so it can be run again in seconds.

👁

Detect

Slow, about 84 minutes for the full video. Saved to a file when done.

🏷

Track

Reads the saved detections, runs in seconds.

✂️

Smooth

Reads the raw tracks, runs in seconds.

🎬

Render

Draws the boxes on a copy of the video. Takes minutes, not hours.

One command, four stages

The run command runs the whole pipeline: all four stages. Each one writes its output, and the next one picks it up.

CODE 

do_detect(args.video, args.start_frame, args.end_frame, p["dets"])
do_track(args.video, p["dets"], p["raw"])
do_smooth(args.video, p["raw"], p["smooth"])
do_render(args.video, p["raw"], p["raw_video"], args.debug_height, "RAW")
do_render(args.video, p["smooth"], p["smooth_video"], args.debug_height, "SMOOTHED")
PLAIN ENGLISH

First, spot the cars in every frame in the range, and save those detections.

Next, follow the cars and save the raw tracks, before any clean-up.

Then run the editor, and save the cleaned tracks next to the raw ones.

Draw a video from the raw tracks, so you can compare it with the editor's version.

Draw a second video from the cleaned tracks.

One row, one car, one frame

Every output file is a Parquet table. Each row is one car in one frame, with the same columns in every file. Those columns are a fixed contract.

frame_idx Which frame of the video this row belongs to, counted from zero.
timestamp_s When that frame happened, in seconds, taken from the video file.
track_id The name badge. The same car keeps the same number across its rows.
class_name What the car is, such as car, bus or truck.
anchor_x, anchor_y The bottom centre of the box, where the car meets the road. Used for every road calculation.
📦
Why store the settings with the output

Each file records the frame range, the frame rate read from the video, and the model used. Six months from now, you can tell what produced it.

Where the project stands

The chain works end to end on a 30-second test. Some problems are known and not yet fixed.

🛵
Motorcycles are often missed

Deferred. The spotter needs more detail to see them.

🔭
Cars at the top of the frame start late

The spotter sees them earlier, but with low confidence, so the tracker does not start them until later.

🙈
Hidden cars lose their badge

Stitching bridges gaps of up to 2 seconds. Longer hiding is not fixed yet.
